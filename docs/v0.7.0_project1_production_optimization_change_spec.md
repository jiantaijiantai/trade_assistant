# Project1 v0.7.0 生产化优化修改说明书

## 版本信息

- 版本号：v0.7.0
- 项目：project1 / trade_assistant
- 文档类型：修改说明书
- 修改目标：将当前 MVP 从“可演示的多 Agent 业务助手”推进到“具备准生产安全边界、可恢复执行、可评测迭代”的内部业务系统原型。
- 修改范围：Supervisor 路由、LangGraph 执行状态、预算计量、身份与 ACL、评测体系、业务工具开放策略。

## 背景判断

当前系统已经具备多 Agent 路由、本地 RAG、工具白名单、逻辑成本检查、基础租户元数据过滤和 Loop Engineering 能力。但仍存在以下生产化缺口：

- Supervisor 主要依赖关键词规则，`route_confidence` 存在固定值，不能代表真实置信度。
- LangGraph 执行过程未持久化，长任务不能可靠暂停、恢复、重放。
- `cost_units` 是逻辑预算，无法反映真实 token、金额、工具调用次数和耗时。
- `tenant_id` 已用于 RAG 过滤，但身份来源仍需要从正式认证上下文派生，不能信任前端请求体。
- 评测集规模和对抗覆盖不足，难以支撑路由、检索、生成、工具执行的版本化回归判断。
- 工具目前适合低风险本地生成，后续连接真实业务系统时必须采用“只读优先、受控写入”的渐进策略。

## 总体结论

本版本优化方案可行，且建议按照“安全边界优先、可观测预算其次、智能路由再次、长任务状态机随后、评测体系贯穿全程”的顺序推进。

不建议直接把 Agent 接入核心业务系统执行写操作。应先接入只读数据源，验证权限、审计、检索准确性和业务收益后，再逐步开放低风险、幂等、可审批、可回滚的写操作。

## 修改目标

### 1. Supervisor 混合路由升级

将当前关键词 Supervisor 升级为“规则优先、模型补充”的混合路由。

目标能力：

- 高确定性业务关键词继续走规则路由。
- 未命中或存在歧义的请求交给结构化分类模型。
- 模型输出必须包含 `task_type`、`confidence`、`reason`、`missing_fields`、`risk_flags`。
- 引入标注集校准置信度，禁止使用固定 `0.8` 表示真实置信度。
- 低置信度请求进入澄清节点，而不是默认进入知识问答。

建议实现：

- 新增 `routing/classifier.py`：封装结构化路由分类。
- 新增 `routing/rules.py`：保留高精度关键词规则。
- 新增 `routing/schemas.py`：定义统一 `RouteDecision` schema。
- 修改 `agents/base_agents.py` 中 `Supervisor.route()`。
- 修改 `graph/production_graph.py` 中 `supervisor_node()`，使用真实 `decision.confidence`。
- 新增 `clarification_node`，低置信度时返回澄清问题。

验收标准：

- 固定 `route_confidence = 0.8` 被移除。
- 路由结果可解释、可回放、可评测。
- 对模糊请求不会静默走错 Agent。

### 2. LangGraph 检查点与任务状态机

为 LangGraph 引入持久化 checkpointer，并建立明确的任务状态机。

目标能力：

- 长任务可以暂停、恢复和重放。
- 每个节点状态可审计。
- 写操作、高风险工具、低置信路由前可以进入人工审批。
- 重放时可复用历史输入、路由决策、工具计划和审批结果。

建议状态：

```text
created
-> routed
-> planning
-> waiting_approval
-> running
-> succeeded
-> failed
-> cancelled
-> replayed
```

建议实现：

- 新增 `core/task_state.py`：定义任务状态枚举和状态转换约束。
- 新增 `core/checkpoints.py`：封装 LangGraph checkpointer。
- 修改 `graph/production_graph.py`：编译 graph 时注入 checkpointer。
- 新增 `approval_node`：处理人工审批、拒绝、超时。
- API 增加任务查询、恢复和重放接口。

建议接口：

- `POST /tasks`：创建任务。
- `GET /tasks/{task_id}`：查询任务状态。
- `POST /tasks/{task_id}/approve`：审批继续执行。
- `POST /tasks/{task_id}/resume`：恢复任务。
- `POST /tasks/{task_id}/replay`：按历史输入重放。

验收标准：

- 服务重启后任务状态不丢失。
- 人工审批节点可以阻断写操作。
- 同一任务可按版本和 checkpoint 重放。

### 3. 真实预算与用量计量

保留 `cost_units` 作为业务抽象，但必须补充真实用量指标。

目标能力：

- 记录 input token、output token、总 token。
- 记录模型调用金额或估算金额。
- 记录工具调用次数、检索次数、重试次数。
- 记录节点耗时和总耗时。
- 支持按 tenant、user、task、tool 聚合用量。

建议实现：

- 新增 `core/usage.py`：定义 `UsageLedger`、`UsageEvent`、`ExecutionBudget`。
- 扩展 `RequestContext`：增加真实预算字段，例如 `max_tokens`、`max_tool_calls`、`max_duration_ms`、`max_estimated_cost`。
- 修改 `_run_agent()`：每个 Agent 输出用量事件。
- 修改工具执行器：每次工具调用写入用量事件。
- 最终响应中区分“业务成本单位”和“真实资源消耗”。

验收标准：

- 不再只依赖 `current_cost_units` 判断预算。
- 每次请求能输出完整资源消耗摘要。
- 超预算能在执行中提前停止，而不是事后统计。

### 4. 身份系统与后端强制 ACL

将应用层 `tenant_id` 升级为后端强制 ACL 和正式身份上下文。

当前已有基础：

- RAG 元数据中已有 `tenant_id`、`department_id`、`visibility`、`allowed_roles`、`allowed_groups`、`allowed_user_ids`、`sensitivity_level`。
- 检索中已有 tenant 和 department 过滤。
- 命中后已有 ACL 二次过滤。

需要补强：

- `tenant_id`、`user_id`、`roles`、`department_ids`、`groups`、`clearance_level` 必须从认证系统派生。
- 前端请求体中的身份字段只能作为开发模式 fallback，生产模式必须禁用。
- 数据库查询、向量检索、工具执行统一经过 policy 层。
- 高敏资料建议使用租户独立 collection 或独立索引。
- 所有权限拒绝必须写审计日志。

建议实现：

- 新增 `core/auth.py`：从 token/session 派生 `Principal`。
- 新增 `core/policy_engine.py`：统一授权判断。
- 修改 `api.py`：生产模式下禁止信任请求体身份字段。
- 修改 RAG 和工具执行入口：强制接收后端生成的 `RequestContext`。
- 增加权限越界测试样本。

验收标准：

- 普通用户无法通过修改请求体访问其他 tenant 或 department 数据。
- 工具执行权限与 RAG 访问权限一致。
- 权限拒绝可审计、可追踪。

### 5. 版本化评测体系

扩大评测集并建立版本化实验机制。

评测模块：

- `routing_eval`：路由准确率、低置信澄清率、误路由率。
- `retrieval_eval`：Recall@K、MRR、证据覆盖率、权限过滤正确率。
- `generation_eval`：事实一致性、引用完整性、不可判断拒答率。
- `tool_eval`：工具选择准确率、参数完整率、幂等命中率、审批触发率。
- `security_eval`：权限越界、Prompt Injection、冲突文档、重复提交防护。

必须加入的对抗样本：

- 错误合同编号。
- 多份冲突文档。
- 跨租户或跨部门资料访问。
- Prompt Injection 要求忽略权限或泄露资料。
- 重复提交同一业务动作。
- 模糊请求要求系统自行猜测业务对象。
- 高风险写操作伪装成普通查询。

建议实现：

- 新增 `evals/datasets/`：存放版本化样本。
- 新增 `evals/runners/`：按模块运行评测。
- 新增 `evals/results/`：保存每次实验结果。
- 每次实验记录模型版本、prompt 版本、索引版本、代码版本、数据集版本。

验收标准：

- 每次路由、检索、生成和工具改动都能跑回归。
- 评测报告能定位是 prompt、模型、索引、规则还是工具策略导致的变化。
- 安全类样本必须作为发布阻断项。

### 6. 业务能力开放策略

业务工具开放应按风险分层推进。

阶段建议：

1. 只读数据源：合同、结算单、发票、货转、客户资料等只读查询。
2. 本地草稿生成：生成检查清单、报告草稿、待办建议，不写核心系统。
3. 低风险受控写：创建内部待办、生成草稿单据、写入非核心工作台。
4. 审批后写入：需要人工审批后才能提交到正式业务系统。
5. 高风险写操作：付款、合同生效、发票开具、客户准入变更等暂不建议由 Agent 直接执行。

工具准入要求：

- 有明确输入输出 schema。
- 有幂等 key 和唯一约束。
- 有权限检查。
- 有审批策略。
- 有审计日志。
- 有失败回滚或补偿方案。
- 有评测样本覆盖。

## 推荐实施顺序

### P0：安全与可追踪基础

- 接入正式身份上下文。
- 禁止生产模式信任请求体身份字段。
- 统一 ACL policy 层。
- 增强审计日志。
- 增加权限越界评测样本。

### P1：真实用量和预算

- 新增真实 token、金额、工具次数、耗时统计。
- 每个 LangGraph 节点写入用量事件。
- 超预算提前终止。

### P2：混合路由与澄清节点

- 保留高确定性规则。
- 引入结构化模型分类。
- 移除固定置信度。
- 低置信度进入澄清。

### P3：持久化状态机

- 引入 LangGraph checkpointer。
- 增加任务状态机。
- 增加人工审批节点。
- 增加任务恢复和重放接口。

### P4：版本化评测与实验

- 建立模块化评测集。
- 增加对抗样本。
- 将安全评测设为发布阻断。
- 保存实验结果和版本元数据。

### P5：受控连接真实业务系统

- 先连接只读数据源。
- 再开放低风险本地或工作台写入。
- 最后考虑审批后写核心系统。

## 不建议事项

- 不建议让 Agent 直接操作核心业务系统。
- 不建议把固定置信度当成模型判断结果。
- 不建议只靠前端传入 `tenant_id` 做隔离。
- 不建议没有幂等唯一约束就开放写操作。
- 不建议没有评测集就频繁改 prompt 或模型。
- 不建议在没有审批节点的情况下执行高风险工具。

## 发布门槛

v0.7.0 完成后，至少满足以下条件才建议进入下一阶段：

- 路由不再使用固定置信度。
- 生产模式身份字段由后端认证上下文生成。
- RAG 和工具执行均经过统一权限检查。
- 每次请求有真实资源消耗记录。
- 长任务具备可恢复或至少可追踪状态。
- 关键安全评测样本全部通过。
- 写操作仍限制在低风险、本地或审批后执行范围内。
